# Eigen RVV10 后端：工具链打通 + 真机 A/B

- 日期：2026-11-16
- 上游：`eigen/eigen` @ `1cf2f018d85b220526160e34aa316c6bd89cd38f`
- 真机：SpacemiT K3 / <distro>，`Linux k3 6.18.3 riscv64`，RVV 1.0，**vlenb=32 / VLEN=256**
- 结论：**RVV10 后端可用，真机 A/B 逐字节一致，整数 9.4×、双精度 17.6×**

## 1. 卡点与解法

上游 `Eigen/src/Core/arch/RVV10/` 已有完整后端（`PacketMath{,2,4}.h`、`TypeCasting.h`、
`GeneralBlockPanelKernel.h`），但 `ConfigureVectorization.h:106` 的门控是

```c
#if defined(EIGEN_RISCV64_USE_RVV10) && defined(__riscv_v_fixed_vlen)
```

`__riscv_v_fixed_vlen` 来自编译器的定长向量契约，不是 `-march` 的副产物：

| 编译器 | `-march=rv64gcv_zvl256b` | 加 `-mrvv-vector-bits=zvl` | 结果 |
|---|---|---|---|
| GCC 13.3（`rvv-cross:1/2` 默认） | 只给 `__riscv_v_min_vlen 256` | **选项不认识** | `member variables cannot have RVV type` |
| GCC 14.2（`g++-14-riscv64-linux-gnu`） | 只给 `__riscv_v_min_vlen 256` | **认，且给出 `__riscv_v_fixed_vlen 256`** | 编过 |
| GCC 15.2（真机 <distro> 自带） | 只给 `__riscv_v_min_vlen 256` | 认，给出 `__riscv_v_fixed_vlen 256` | 编过 |

即"`-mrvv-vector-bits` 是 Clang 专属选项"这条旧结论**只对 GCC 13 成立**，GCC 14 起已支持。
另外 GCC 13 会忽略 `__attribute__((riscv_rvv_vector_bits(N)))`（`PacketMathDecl.h:76`），
所以向量类型不能作成员——这也是 `GeneralPacketMath.h:238` 报错的根因，与宏无关。

### 最终编译命令（两侧同一条，唯一变量是宏）

```bash
M="-march=rv64gcv_zvl256b -mrvv-vector-bits=zvl -O2 -I src -static"
g++ $M                        test/pkg_eigen.cpp -o harness_off
g++ $M -DEIGEN_RISCV64_USE_RVV10 test/pkg_eigen.cpp -o harness_on
```

`-march=rv64gcv_zvl256b` 让代码生成按 VLEN=256 优化，`-mrvv-vector-bits=zvl` 把它绑定成
定长向量契约（Eigen 的 packet 大小依赖它）。两者必须成对出现，只给前者后端不启用。

## 2. qemu 的功能结论不可信（新教训）

容器 GCC 14.2 编出的两侧在 qemu（`-cpu rv64,v=true,vlen=256`）下：

```
off imatmul 64x64 fnv=b6934bd0094dc25a
on  imatmul 64x64 fnv=70008b1ef18c9fc1   ← 不一致
```

同一份代码搬到真机（GCC 15.2 原生编）→ 两侧哈希完全相同。**qemu 对 RVV10 的整数
kernel 模拟有缺陷**，不只是计时不可信，功能判定也不能采信。凡涉定长向量契约与
多寄存器整数累加的 kernel，qemu 只能当"能启动"的冒烟测试。

## 3. 真机 A/B（GCC 15.2 原生，5 轮 × best-of-5，三轮重复）

| 用例 | off（标量 C++） | on（RVV10） | 加速 |
|---|---|---|---|
| `imatmul 64×64`（int32） | 0.646 ms | **0.068–0.069 ms** | **9.4×** |
| `dmatmul 128×128`（double） | 13.459–13.474 ms | **0.765–0.767 ms** | **17.6×** |

功能门禁：

```
imatmul 64x64 fnv=b6934bd0094dc25a  mismatch=0/4096     ← 逐元素与标量参照全等
dmatmul 128x128 fnv=72dccc2fcdc7d3ba max_rel=2.346e-13 ← 容差 1e-6 内
BYTES_SAME（round1/2/3 全 SAME）
```

整数路径原来有"哈希不一致"的疑点，加 `mismatch` 计数后定性为 qemu 模拟问题：
真机 `mismatch=0/4096`，4096 个元素全等于标量参照。

## 4. 归因

- **整数 9.4×**：64×64 规模小，主要吃 packet 化的 8 路 int32 `vmacc`；规模一大
  内存带宽与 block panel 拷贝占比上来，故低于浮点的 17.6×。
- **双精度 17.6×**：128×128 的 `X*X^T` 是 Eigen 最成熟的分块 GEMM 路径，VLEN=256 下
  双精度 packet = 4 元素，RVV10 的 `vmacc` 与转置拷贝都走了向量。
- 与 x86 AVX2 的经验区间一致（Eigen 在 SSE/AVX 上的 GEMM 加速通常 8–20×）。

## 5. 口径

Eigen 归入"上游自带向量实现"（第 8 个）：内核在 `arch/RVV10/`，我们做的是
①工具链打通（GCC ≥ 14 + `-mrvv-vector-bits=zvl`）；②建立两侧同编译器同 march、
唯一变量为 `EIGEN_RISCV64_USE_RVV10` 的 A/B；③真机功能门禁 + 量化。
不写新内核，因此 G3 的"内核差分"证据为上游后端的自身等价性。

## 6. 复现

```bash
# 真机（推荐：GCC 15.2 原生，无 qemu 失真）
cd /root/rvv-k/eigen && M="-march=rv64gcv_zvl256b -mrvv-vector-bits=zvl -O2 -I src -static"
g++ $M test/pkg_eigen.cpp -o harness_off
g++ $M -DEIGEN_RISCV64_USE_RVV10 test/pkg_eigen.cpp -o harness_on
./harness_off /tmp/o.bin 5; ./harness_on /tmp/n.bin 5; cmp /tmp/o.bin /tmp/n.bin && echo SAME

# 容器（GCC 14，仅冒烟，功能结论需真机复核）
docker run --rm -v $PWD:/work -w /work rvv-cross:2 bash -lc \
  'apt-get install -y -qq g++-14-riscv64-linux-gnu; riscv64-linux-gnu-g++-14 -march=rv64gcv_zvl256b -mrvv-vector-bits=zvl -DEIGEN_RISCV64_USE_RVV10 -O2 -I src test/pkg_eigen.cpp -static -o /tmp/on'
```
